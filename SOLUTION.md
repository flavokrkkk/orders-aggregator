## Причина расхождения из жалобы

Расхождение дают **две** ошибки, обе исправлены.

### 1. День заказа считался по смещению таймзоны «на сейчас», а не на момент заказа (основная)

`TotalsService.daily` вычислял смещение один раз: `tzOffsetMinutes(timezone, new Date())`, и применял его ко всем заказам
периода. `c_7` — `Europe/Berlin`. 29.03.2026 в 01:00 UTC Берлин переходит с UTC+1 на UTC+2. Сейчас (ноябрь) смещение
UTC+1, поэтому до перехода (27–28.03) всё совпадает, а после него заказы, созданные с 22:00 до 23:00 UTC, попадают
в предыдущий день:

| Заказ | createdAt (UTC) | Сумма | В Берлине (UTC+2) | Старый код (UTC+1) |
|---|---|---:|---|---|
| o_02357 | 2026-03-29 22:40 | 9 306 | 30.03 00:40 | 29.03 23:40 |
| o_02448 | 2026-03-30 22:40 | 1 823 | 31.03 00:40 | 30.03 23:40 |
| o_02545 | 2026-03-31 22:15 | 5 487 | 01.04 00:15 | 31.03 23:15 |
| o_02547 | 2026-03-31 22:40 | 4 999 | 01.04 00:40 | 31.03 23:40 |

Ответ при этом ещё и зависел от даты запроса: летом тот же запрос дал бы ошибку уже на 27–28.03.

**Исправление:** агрегация переехала в SQL (`OrdersRepository.paidDailySums`). День считается как
`(created_at AT TIME ZONE tz)::date`, то есть по правилам таймзоны в момент каждого заказа, а границы периода — как местная
полночь в таймзоне клиента (`(from::date)::timestamp AT TIME ZONE tz`). Заодно сервис больше не тянет все заказы периода
в память: суммы считает БД, по индексу `(customer_id, status, created_at)`.

### 2. Гонка при параллельных вебхуках: терялись обновления

`OrdersService.apply` делал «прочитать текущую версию → сравнить `updatedAt` → записать» без блокировки. Внешний API
шлёт вебхуки с повторами, не по порядку и параллельно (я видел до 3 одновременных запросов). Два параллельных запроса
читают одну и ту же старую версию, оба решают, что их версия новее, и побеждает тот, кто запишет последним, даже
если его версия старше.

На исходном коде это воспроизвелось: `o_02281` (3 675 ₽, 29.03) остался `paid` с версией 03:50, хотя последняя версия
(04:50) — `refunded`. Отсюда разница 47 639 − 43 964 = 3 675 за 29.03 сверх ошибки с таймзоной. Ошибка недетерминированная,
от прогона к прогону задевает разные заказы.

**Исправление:** проверка и запись — один атомарный запрос
`INSERT … ON CONFLICT (id) DO UPDATE … WHERE orders.updated_at < excluded.updated_at RETURNING (xmax = 0)`
(`OrdersRepository.upsertIfNewer`). Нет строки в ответе — `stale`, `xmax = 0` — вставка, иначе обновление.

### Как нашёл

1. По формулировке («часть дней в конце марта», «считаем в таймзоне клиента») сразу заподозрил переход на летнее время;
   в `totals.ts` нашёлся `tzOffsetMinutes(timezone, new Date())`. `GET /customers/c_7` во внешнем API → `Europe/Berlin`,
   переход 29.03.
2. Выгрузил все заказы внешнего API (5 030 штук, скрипт с паузами из-за лимита) и перехватил вебхуки локальным
   HTTP-сервером (92 доставки по 21 заказу `c_7`).
3. Написал независимый от кода сервиса расчёт: итоговая версия заказа = максимальный `updatedAt` из синка и вебхуков,
   день — через `Intl.DateTimeFormat` в `Europe/Berlin`. Тот же расчёт со смещением «на сейчас» воспроизвёл расхождение
   ровно на 29–31.03 и показал, какие заказы «переезжают» (таблица выше).
4. Прогнал полный сценарий на исходном коде: 29.03 расходилось с моим расчётом ещё на 3 675 ₽. В БД нашёл `o_02281`
   в устаревшем статусе → гонка в `apply`.

## Что сделано

### Скидки в `daily-totals`
- Ответ: `[{ date, total, gross, discount, net }]`. `gross` — сумма оплаченных заказов до скидки, `net` — фактически
  оплачено, `discount = gross − net`, `total = gross`.
- Всё считается в копейках, в рубли переводится только в ответе. `discount` — разность копеек, а не разность
  округлённых рублей.
- Миграция `002_discounts.sql`: колонки `discount_percent NUMERIC(5,2)` и `amount_paid_kop BIGINT` (с CHECK).
- Разбор полей внешнего API (`OrdersService.normalize`):
  - `amountPaid` — источник правды для `net` (это то, что клиент фактически заплатил);
  - нет `amountPaid`, но есть `discountPercent` → оплата = `amount × (100 − %) / 100`, доли копейки отбрасываются
    (как и везде в сервисе);
  - нет обоих полей (старые заказы) → скидки нет, `net = gross`;
  - числа и строки принимаются оба (API присылает и так, и так);
  - `discountPercent` вне 0..100, `amountPaid > amount`, мусор вместо числа → `ValidationError`
    (вебхук → 400, в синке такой заказ попадает в `invalid`).
- **Совместимость с уже сохранёнными данными.** Строки, сохранённые до этой версии, получают `NULL` в новых колонках
  (в статистике для них `net = gross`). Обычный синк их бы не обновил: `updatedAt` тот же → `stale`. Поэтому
  `upsertIfNewer` перезаписывает строку и той же версией, если у неё `amount_paid_kop IS NULL`, а у входящей версии — нет.
  После деплоя достаточно одного `POST /sync` (описано в README). Покрыто тестом.

### Исправления
1. **Таймзона / переход на летнее время** — см. выше.
2. **Гонка в `apply`** — см. выше.
3. **Потеря копейки в `toKop`.** `Math.floor(rub * 100)` на float: `4723.9 * 100 = 472389.99999999994` → 472 389 коп.
   В данных внешнего API таких `amountPaid` 96 штук, то есть `net` занижался бы. Теперь сумма сначала округляется
   до 6 знаков (убирает погрешность двоичного представления), потом отбрасываются доли копейки. Существующий контракт
   «доли копейки отбрасываем» (`toKop(10.999) = 1099`) сохранён.
4. **`.env` не читался.** README предлагает `cp .env.example .env`, но ни сервис, ни тесты его не загружали: без
   экспортированных переменных всё молча шло на дефолтный `localhost:5432`. У меня на этом порту оказалась чужая база,
   и сервис пытался подключиться к ней. Теперь `config.ts` и `vitest.config.ts` вызывают `process.loadEnvFile()`;
   переменные окружения процесса приоритетнее.
5. **Ошибки Fastify отдавались как 500.** Глобальный обработчик превращал всё, что не `AppError`, в 500: битый JSON
   или неверный `content-type` во вебхуке → 500, и отправитель ретраил бы заведомо плохой запрос. Теперь 4xx от Fastify
   пробрасываются как есть.
6. `parseRub("")` возвращал 0 (`Number("") === 0`), теперь это ошибка.
7. Период в `daily-totals` ограничен 366 днями: ответ содержит строку на каждый день, без лимита один запрос мог бы
   сгенерировать огромный массив.

они сравнивали ответ через `toEqual` с точной формой `{ date, total }`, а задание требует новые поля. Суммы
в ожиданиях не тронуты.

Новые файлы:
- `test/timezones.test.ts` — весенний и осенний переход (Berlin), границы периода в таймзоне клиента, ровно полночь,
  южное полушарие (`America/Santiago`), лимит периода;
- `test/discounts.test.ts` — пример из задания, суммы по дням, float-суммы, строковые поля, старые заказы без скидки,
  только `discountPercent`, исключение `pending`/`refunded`, обновление скидки вебхуком, валидация, хранение

- `test/concurrency.test.ts` — 16 параллельных вебхуков (8 версий × 2 повтора, в случайном порядке, 5 раундов) →
  побеждает самая свежая; одновременная доставка нового заказа → ровно один `created`;

## Как проверял результат

1. **Регрессионные тесты падают на старом коде.** Прогнал `timezones.test.ts` и `concurrency.test.ts` на исходной
   версии сервиса: 7 из 7 падают. На исправленной — проходят. Набор целиком (53 теста) прогнал несколько раз подряд,
   чтобы исключить флаки: стабильно зелёный. `npm run typecheck` чистый.
2. **Независимый расчёт.** Ответ сервиса сверил с отдельным скриптом, который не использует код сервиса: сырые данные
   внешнего API (выгрузка `/orders` + перехваченные вебхуки) → последняя версия каждого заказа по `updatedAt` → день
   через `Intl` в `Europe/Berlin` → суммы в копейках. `result.json` совпал с ним побайтно.
3. **Сквозной сценарий из TASK.md** (`docker compose down -v && up -d`, чистая БД → `npm start` → `POST /sync` → вебхуки
   командой из README → `daily-totals`) — прогнал дважды с нуля, результат идентичен. Потом повторно доставил все
   вебхуки и повторно сделал синк: ответ не изменился (синк вернул `stale: 5030`).
4. **Было/стало.** Тот же сценарий на исходном коде дал цифры из первой таблицы. Разница объясняется полностью:
   4 заказа из-за таймзоны (−9 306 / +7 483 / −8 663) плюс потерянный `refunded` у `o_02281` (+3 675 за 29.03).

## Что заметил во внешнем API

- **Вебхуки:** 92 доставки для 21 заказа: повторы, обратный порядок (старая версия приходит после новой), до 3 запросов
  параллельно. Подписи или иной аутентификации нет. Все вебхуки прогона — по `c_7`.
- **`/orders` не отражает изменений из вебхуков:** повторный синк после вебхуков отдаёт старые версии (у нас все 5 030
  → `stale`). Полный синк — не источник правды, и без проверки `updatedAt` он откатил бы статусы назад.
- **Лимит запросов строже заявленных 5 rps:** `200 {"error":"rate_limited"}` приходил и при ~3.3 rps (пауза 300 мс), без
  `Retry-After`. Клиент сервиса это уже обрабатывает.
- **Курсор** — base64 от `o:<offset>`, то есть пагинация по смещению: если во время синка добавятся или удалятся заказы,
  возможны пропуски и дубли. Конец списка — пустая страница с тем же курсором (уже обрабатывалось).
- **Форматы:** `amount` иногда строкой (`"3100.00"`, 157 заказов), `discountPercent` иногда строкой (`"7"`, 177).
  288 `createdAt` без указателя зоны. Проверил, что это действительно UTC: разница `updatedAt − createdAt` у них
  распределена так же, как у дат с `Z`, и ни разу не отрицательна (будь это местное время, часть разниц ушла бы в минус).
- **Скидки:** у заказов, созданных до 2026-03-15, полей скидки нет. Там, где они есть, `amountPaid` всегда равен
  `amount × (1 − % / 100)` с точностью до копейки, а проценты целые.

## Что ещё заметил в коде (не трогал)

- Таймзона клиента кешируется в БД навсегда (`fetched_at` пишется, но не используется): если клиент сменит таймзону,
  сервис не узнает. Нужен TTL или инвалидация.
- `POST /sync` синхронный: 5 030 заказов — ~16 секунд, с ростом данных упрётся в таймауты прокси или клиента. Защита
  от параллельного запуска — только в памяти процесса: при нескольких инстансах синки пойдут параллельно.
- `HttpOrdersApi`: невалидный JSON в ответе 200 бросает `SyntaxError` и роняет весь синк, вместо ретрая; попытки на 429
  тратятся без нарастающей паузы.
- `/webhooks/order` никак не аутентифицирован: любой может прислать «заказ».
- Утилиты `tzOffsetMinutes` и `dateAtOffset` оставил (на них есть тесты), но в расчёте дней они больше не используются.
  Добавил в комментарий предупреждение, почему фиксированное смещение для дат клиента не годится.

## Допущения

- **`net` берётся из `amountPaid`**, а не пересчитывается из `discountPercent`: поле прямо описано как «оплачено».
  Сейчас оба источника согласованы, но если разойдутся, верим деньгам.
- **Заказы без полей скидки** (старые) — без скидки: `net = gross`, `discount_percent = 0`.
- **`amountPaid > amount` — невалидный заказ**: отрицательная скидка выглядит как ошибка данных, а не как бизнес-кейс.
- **Строки, сохранённые до этой версии** (`amount_paid_kop IS NULL`), до пересинка считаются без скидки.
- **Округление:** доли копейки отбрасываются, как и раньше в сервисе («деньги клиенту не досчитываем»), в том числе
  при расчёте оплаты по проценту.
- **Статистика по текущему статусу:** день — по `createdAt`, учитываются заказы, которые оплачены *сейчас*. Возврат
  задним числом меняет сумму за прошлый день. Так было и до меня, и, судя по совпадению 27–28.03, платёжная система
  считает так же.
- **Один и тот же `updatedAt`** — та же версия (повтор), кроме случая дозаполнения скидок выше.

## Что бы доделал при наличии времени

- Сделать синк асинхронным: `POST /sync` возвращает id запуска, статус — из `sync_runs`. Блокировку от параллельных
  запусков — через `pg_advisory_lock`, чтобы работало и с несколькими инстансами.
- Аутентификация вебхуков (HMAC-подпись) — по согласованию с командой внешнего API.
- TTL для таймзоны клиента, ретрай невалидного JSON в `HttpOrdersApi`.
- Если ответы `daily-totals` по большим периодам станут горячими — материализованные дневные агрегаты, пересчитываемые
  при изменении заказа.
- CI: GitHub Actions с сервисом Postgres, `typecheck` + тесты.
